# Дальнейшая разработка

## Подготовка окружения

Выполните [развёртывание](DEPLOYMENT.md) с `.venv`, прочитайте [архитектуру](ARCHITECTURE.md) и [известные проблемы](KNOWN_ISSUES.md). Проверяйте изменения на `examples/demo` или копии тестовой базы 1С, а не на рабочей базе клиента.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m athena.server --port 8766 --project examples/demo
```

Мастер первоначальной настройки нужно пройти и в новом тестовом окружении. В UI «AI-помощник» и «Агент кода» — отдельные пункты навигации. «Правки», поиск по коду и свойства показываются только в разделе «Код». Генератор открывается из «Документации» или кнопкой «Документировать» в BSL-редакторе. Для проверки фронтенда достаточно браузера. Если Node.js установлен, проверка синтаксиса файлов:

```powershell
node --check web/app.js
node --check web/code-agent.js
node --check web/change-sets.js
node --check web/completion.js
node --check web/documentation.js
```

## Порядок работы

1. Создайте ветку, например `git switch -c codex/agent-search-progress`.
2. Зафиксируйте конкретный сценарий, текущий результат и ожидаемое поведение. Проверьте, что не меняются инварианты архитектуры.
3. Внесите ограниченное изменение и регрессионный тест, который воспроизводит причину ошибки, а не просто повторяет реализацию.
4. Выполните относящиеся к изменению тесты, затем полный набор. Для UI проверьте реальный переход и результат в браузере.
5. Для поведения модели отдельно проведите проверку с настоящей моделью. Сохраняйте безопасную трассу и точный результат; HTTP-заглушки проверяют протокол, но не качество модели.
6. Обновите документацию и известные проблемы. Опишите в коммите/PR проблему, итоговое поведение, проверки и ограничения.

Не удаляйте кеши пользователя для удобства тестирования. Тесты создают временные проекты; новые тесты должны следовать тому же подходу. Не импортируйте тестовые изменения в рабочую информационную базу.

## Приоритет ближайшего этапа

Проверьте реальные сценарии из `KNOWN_ISSUES.md` после подключения создания объектов и защиты от повторных обходов. Механизмы памяти и завершения без прогресса уже покрыты автоматическими тестами; это не подтверждает качество настоящей модели. Следующие проверки: находит ли агент нужный обработчик, предлагает ли фактические изменения и объясняет ли пустой результат.

Для генератора документации расширяйте полноту контекста крупных проектов и проверку фактических утверждений. Сейчас используются статические материалы в пределах лимита символов; тесты подтверждают передачу выделения, хеши, отмену, сохранение и HTTP-контракты, но не смысловую точность документа. Скилл и оригинальный шаблон версионируются в `athena/skills/documentation-generator/`; при изменениях проверяйте размер системного сообщения и доступный бюджет исходников.

После этого: проверка контекстов доступности платформы, анализ типов для подсказок, более полная проверка конфигурации 1С перед загрузкой, управление размером выгрузок и индексов, воспроизводимая упаковка приложения. Выбор другой БД или полноценной редакторской библиотеки — отдельное архитектурное изменение; сейчас используется SQLite и редактор проекта.

## Работа с парсером, индексом и зависимостями

Сгенерированные файлы ANTLR не редактировать вручную. Источник, лицензии и команда генерации находятся в [PROVENANCE.md](../athena/bsl_grammar/PROVENANCE.md). Для генерации нужен Java и соответствующий ANTLR; для выполнения приложения Java не требуется.

Изменение результата разбора требует обновления версии/рецепта парсера и тестов кеша. Изменение схемы SQLite — миграции с сохранением данных и теста открытия прежней базы. Изменение модели/рецепта эмбеддингов должно давать отдельную идентичность индекса, не переиспользовать несовместимые векторы.

Зависимости заданы в `requirements.txt`: часть закреплена, `numpy` задан диапазоном, транзитивные зависимости не закреплены полным lock-файлом. Поэтому установка пока не полностью воспроизводима. Не добавляйте `pip freeze` из общей среды автора: в ней есть посторонние библиотеки. При подготовке релиза создайте lock из чистого окружения, проверьте платформы и повторную установку.

## Перед публикацией или релизом

```powershell
git status --short
git diff --cached --stat
git diff --cached
```

В Git должны попадать только исходники, минимальные шаблоны, лицензии зависимостей, учебные файлы, тесты и документация. `.athena`, `.venv`, реальные конфигурации клиента, SQLite, учётные данные и локальные журналы не публиковать. Не копируйте рабочую выгрузку в `examples` — этот каталог входит в Git.

Право распространения собственного кода проекта должен определить владелец. Сейчас общая open-source лицензия не назначена. Условия сторонней грамматики сохраняются независимо от выбранной впоследствии лицензии проекта.
